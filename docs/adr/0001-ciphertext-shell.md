# ADR-0001：密文外壳——按加密设计，但延后启用

- 状态：已采纳
- 日期：2026-11-04
- 决策人：开发执行方

## 背景

需求 6.1 要求端到端加密（服务端只见密文），需求 4.2 要求块级合并（服务端要能判断并发）。
两者存在结构冲突：服务端看不到内容，就不能做内容合并。同时需求把 E2EE 排在 M3，
若 M1/M2 按明文建模，M3 补加密等于重做数据层。

## 决策

**数据模型与协议从第一天就按密文设计，但当前阶段不启用真加密。**

1. 块内容一律存 `bytea` + `enc` 标记（`none` | `aes-256-gcm`），当前为 `none`，明文透传。
2. 服务端可见的只有一份**明文元数据白名单**：块 ID、类型、顺序键、版本向量、HLC、墓碑、媒体引用、尺寸时长。
3. 冲突仲裁只依赖元数据，因此协议在加密前后完全一致。
4. 客户端提交块时带 `${diaryId}|${blockId}|${deviceId}|${hlc}` 作为 AAD，启用加密后直接复用。

## 后果

- 启用加密 = 切 `keyring.mode` + 接密钥树，不改表结构、不改同步协议、不改合并逻辑。
- 明文元数据会泄露"某天写了含视频的日记"，但不泄露任何内容。这是可接受的取舍，需在隐私说明中写明。
- 媒体去重按用户隔离（keyed hash 由客户端计算），服务端无法跨用户比对文件。

## 备选方案

| 方案 | 否决原因 |
|---|---|
| 先明文建模，M3 再加加密 | 需要重加密全部历史块并改协议，返工风险最高 |
| 整篇日记加密成一个 blob | 块级并发合并、部分同步、墓碑清理全部无法实现 |
| 服务端托管密钥 | 不满足 6.1 的端到端语义，且不能对外宣称加密 |
