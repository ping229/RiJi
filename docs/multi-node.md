# 多节点全量副本部署

本文说明如何把第二个节点加入集群，以及故障时怎么办。
对应需求 4.5（全量副本）、7.2（迁移与校验）、10.4（组网）。

## 原理

- **每个节点保存全量数据**，节点之间不共享数据库、不共享对象存储（需求 10.1）。
- 客户端写入只提交主节点，主节点本地持久化成功即返回，副本异步追平（需求 4.5.3）。
- 主节点把每次变更写入 `replication_log`；副本按游标持续拉取并**幂等应用**。
- 新媒体按需回源，不整库搬运。
- 副本每轮同步后向主节点上报心跳与游标，后台据此显示"落后主节点的变更数"。

## 新增一个副本节点

### 1. 准备一台新机器

要求：Ubuntu 22.04/24.04 或 Rocky 9，磁盘 ≥ 当前集群数据总量 × 1.2，已装 PostgreSQL 16+。

### 2. 用独立环境变量启动

```bash
export RJJ_PORT=8081
export RJJ_DATABASE_URL='postgres://riji:密码@127.0.0.1:5432/riji_replica'
export RJJ_MEDIA_DIR='/data/riji/media'
export RJJ_JWT_SECRET='与主节点完全一致'
export RJJ_REPLICATION_TOKEN='节点间共享令牌'
export RJJ_NODE_ID='node-replica'
export RJJ_NODE_ROLE='replica'
export RJJ_PRIMARY_URL='https://api.example.com'
npm start
```

要点：

- `RJJ_DATABASE_URL` 必须指向**本机独立的库**，不能与主节点共用。
- `RJJ_NODE_ID` 全网唯一。
- 副本节点**不会自建管理员**，账号统一从主节点复制过来。
- `RJJ_JWT_SECRET` 必须与主节点一致，否则客户端令牌在副本上无效。

### 3. 首次启动会自动做全量基线同步

顺序是：用户 → 日记 → 块 → 媒体。日志里会看到：

```
基线同步完成：3 篇日记、8 个块
基线媒体补齐：3 个文件
```

之后每秒轮询增量，日志出现 `[replica] 应用 N 条变更，游标 X/Y`。

### 4. 在主节点后台登记该节点

管理员后台 → 节点管理 → 加入节点，填写节点标识与地址。
随后会显示它的在线状态、最后心跳时间、落后变更数。

## 验证

在任意节点上执行：

```bash
curl -H "x-replication-token: <令牌>" http://127.0.0.1:8081/api/replication/status
```

返回 `cursor` 与 `lag`。`lag` 归零即代表追平。

## 故障处理

### 主节点故障

1. 确认副本数据可用：副本上 `/healthz` 正常、能读日记。
2. 在任一存活节点的后台把某个副本**提升为主节点**（后台 → 节点管理 → 提升为主）。
   提升会递增 epoch，原主节点恢复后必须降级，避免双主写入。
3. 客户端会自动切到 `readEndpoints` 里可用的节点。

> 自动提升默认关闭（需求 4.4），避免误切。

### 节点数据落后或损坏

在后台对该节点执行"全量同步"（对应 `syncMissingMedia` 与基线重放）。
当前版本的基线同步只在节点**本地为空**时触发；若需要强制重同步，先清空该节点数据目录与数据库，再重启。

### 节点退役

后台 → 节点管理 → 准备退役。系统会先检查其他节点是否有完整副本；若这是唯一持有全量数据的节点，会被阻止并告警（返回 `UNIQUE_COPY`）。

## 当前限制（后续版本补齐）

| 限制 | 说明 |
|---|---|
| 节点间 mTLS 已可用 | 证书由 openssl 生成（`npm run certs`），9443 通道强制双向校验；实测：明文端口 403、无证书握手失败、带证书可正常复制 |
| 无自动提主 | 符合需求"默认关闭自动提升"，但目前也没有自动故障检测告警 |
| 增量日志不自动截断 | `replication_log` 会持续增长，后续需要按游标裁剪 |
| 一致性校验只比对数量与摘要 | 跨节点逐块比对尚未实现 |

## 全量同步（后台一键）

副本落后太多、或怀疑数据不一致时，管理员可以在后台「节点」表格里点某个副本的**全量同步**。

机制：

1. 主节点把该节点标记为 `syncing`，记下 `full_sync_requested_at`；
2. 副本在下一次心跳（默认 10 秒内）读到这个标记；
3. 副本把自己的游标清零，从复制日志开头重新拉取；
4. 重放是幂等的，不会产生重复块；
5. 副本回报"已开始"，主节点清掉请求标记，节点回到 `online`。

实测（两节点本机）：

```
下发后：状态=syncing 请求时间=19:35:45
10 秒后：状态=online 游标=26 落后=0 开始时间=19:35:46
主节点块数 15 / 副本块数 15
```

表格里的"同步进度"列会显示：

| 显示 | 含义 |
|---|---|
| 已同步 | 落后 0 条 |
| 落后 N | 有 N 条日志未应用（N > 100 显示红色） |
| 等待开始全量同步 | 指令已下发，副本还没心跳 |
| 全量同步中，落后 N | 副本正在重放 |

**注意**：全量同步期间副本仍可读，但写入会排队到主节点。对大数据量（几十万块）建议在低峰执行。
